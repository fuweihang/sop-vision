# Frontend 测试层级

优先关注用户可见的行为，而非组件内部实现细节。

## 单元测试 (Unit)

适用于纯逻辑：格式化函数、选择器 (selectors)、Reducer、状态机、验证逻辑、确定性转换以及非 DOM 相关的业务规则。

目录：`frontend/tests/unit/<module>/...`

## 组件测试 (Component)

适用于单个 UI 组件或小型组件组合的有意义行为：可见状态、交互、无障碍 (a11y) 行为、启用/禁用状态以及触发的用户操作。

应模拟用户的视角来查询和断言 UI 状态。不要测试 Hook、内部状态变量、特定于实现的类名或子组件的调用次数。

目录：`frontend/tests/component/<module>/...`

## 集成测试 (Integration)

适用于跨组件、Store/状态管理、路由、异步请求、API 适配器、加载/错误/重试流程、陈旧响应 (stale responses) 及竞态条件等场景下的功能行为。

建议使用模拟 (mock) 网络边界，同时保持前端功能本身的真实性。

目录：`frontend/tests/integration/<module>/...`

## 契约测试 (Contract)

适用于生成的 OpenAPI 类型、API Client 载荷、错误格式和外部协议兼容性，不重复页面交互测试。

目录：`frontend/tests/contract/<module>/...`

## 端到端测试 (E2E)

仅用于需要真实浏览器和系统集成的关键用户旅程。

控制 E2E 测试的数量；不要为每个功能或 API 路径都编写此类测试。

项目当前没有日常 E2E 测试入口。确有必要时先设计独立的运行环境和影响规则，不要直接混入 integration 目录。

## 视觉测试 (Visual)

视觉回归测试属于特殊情况。仅针对关键页面、复杂布局、设计系统基础组件或已知的 CSS 回归高发区域使用。

默认情况下，不要添加快照 (snapshot) 或截图测试。

项目当前没有视觉回归入口。新增前必须同时登记运行命令、基准图管理和失败产物位置。
