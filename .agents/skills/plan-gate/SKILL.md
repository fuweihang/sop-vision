# 方案执行门禁

审核用户显式指定的方案。开始前读取与其直接相关的项目规划、相邻阶段方案和当前代码状态。本 skill 不修改业务代码，也不在审核通过后自动开始实施；只有用户明确要求完善方案时才修改方案文件。

## 审核

检查：

* **项目一致性**：是否符合整体规划和实施顺序，与其他任务无冲突、重复或依赖错误。
* **职责边界**：是否错误纳入其他阶段职责，或遗漏当前阶段必须完成的内容。
* **明确性**：需求、接口、数据流、前置条件、实施步骤和验收标准是否足够明确，无需关键假设即可实施。
* **MVP / 过度设计**：是否满足当前模块的最小完整交付；是否为未确认的未来需求提前引入不必要的抽象、扩展层、通用机制或复杂度。
* **可执行性**：方案是否符合当前代码和依赖状态，步骤能否实际执行，并有明确验证方法。

优先从代码和现有文档中消除疑问，不把可自行确认的事实交给用户决策。

## 门禁

### PASS

全部检查通过时：

`审核结果：PASS`

简要输出方案负责的内容、明确不做的事项和实施时必须遵守的限制。

PASS 只表示方案可以进入后续实施，不代表本 skill 已获得修改代码的授权。

### HITL

存在职责冲突、重要不确定性或需要人为决策的问题时：

`审核结果：HITL`

说明阻塞问题及推荐方案，并只向用户询问无法从现有信息确定的决策。

用户要求或确认修改方案后：

1. 更新指定方案；
2. 重新完整审核；
3. 未 PASS 前禁止实施。

用户只要求审核时，不修改方案文件，只给出具体修改建议。方案明显大到无法在一次任务中可靠实现时，说明需要先拆分，但不要在本 skill 中创建拆分文件。

## 原则

**当前方案应当说明要交付什么、不做什么、依赖什么以及如何验证。不要通过扩大范围或提前设计未确认能力来解决当前问题。**
