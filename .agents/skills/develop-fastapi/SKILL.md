# 开发 FastAPI

先适配目标仓库，再选择最小且完整的实现。不要把某个模板的层级、目录或技术栈机械复制到项目中。

用户只要求评审现有代码或 diff 时保持只读，不进入本 skill 的实施流程。用户要求实现或重构时，修改范围仍以其指定任务为准。

## 必读资料

开始设计或实现前，根据任务读取 [分层与实现规范](references/architecture.md) 中相关章节。涉及数据库写入、并发、外部服务或安全边界时，完整读取对应章节。

实现结束后，完整执行 [接口审查清单](references/review-checklist.md)。

## 工作流程

### 1. 建立项目上下文

1. 阅读适用的 `AGENTS.md`、贡献规范、架构文档和功能契约。
2. 检查 `git status`，保留用户已有改动。
3. 使用 `rg` 找到应用入口、路由注册、相邻模块、调用方、测试、配置和迁移。
4. 从锁文件或项目配置确认 FastAPI、Pydantic、SQLAlchemy 和 Python 的实际版本。
5. 涉及框架或库的行为时，通过可用的官方文档工具获取当前文档，不凭记忆假设 API。

以当前代码和已批准的契约为事实源。文档与实现冲突时，先判断是否属于待实现需求，不要擅自覆盖现有行为。

### 2. 冻结接口契约

修改前明确：

- HTTP 方法、路径和 `operation_id`。
- Path、Query、Header、Body 及其校验规则。
- 成功响应、状态码、响应头和内容类型。
- 错误响应、稳定错误码和异常映射。
- 调用者、角色、租户和资源归属规则。
- 幂等、重试和并发语义。
- 事务边界及提交前后的外部副作用。
- 数据库 Schema、迁移和数据回填。
- 前端、SDK、OpenAPI 或其他调用方的兼容性。
- 日志、缓存和敏感数据边界。

只有协议、数据或外部副作用存在会显著改变结果的歧义时才暂停询问用户。

### 3. 选择最小架构

遵守仓库已有目录。职责保持清晰：

```text
Router / API
    ↓
Application Service / Use Case
    ↓
Domain Rules / Ports
    ↑
Repository / External Adapter
    ↓
Database / Remote Service
```

- Router 只处理 HTTP、校验、依赖调用和响应转换。
- Service 编排业务规则、权限和事务，不依赖 FastAPI。
- Repository 封装查询和持久化，不自行提交事务。
- Adapter 隔离第三方 SDK、远程协议、超时和异常。
- Composition Root 组装具体实现；请求状态不得放入全局单例。

简单只读接口可以更扁平。只有在规则复用、替换边界或测试隔离确有价值时才增加 Domain、Port、Mapper 或 UoW。

### 4. 按依赖方向实现

推荐顺序：

1. 请求与响应 Schema。
2. 应用层输入、输出和业务异常。
3. Port 或最小依赖接口。
4. ORM 与迁移（如有）。
5. Repository 或外部 Adapter。
6. Service 与事务边界。
7. 依赖装配。
8. Router、异常处理器和路由注册。
9. 测试、OpenAPI、调用方和文档。

保持现有协议兼容，除非任务明确要求破坏性变更。

### 5. 处理事务与并发

- 一个业务用例使用一个明确事务。
- Router 和 Repository 不 `commit()`。
- 同一用例中的 Repository 共享同一 Session/UoW。
- 异常路径回滚；读取不做无意义提交。
- 外部网络调用不要无意中延长数据库事务。
- 唯一性使用数据库约束；状态前置条件使用原子 SQL、锁或版本字段。
- 不用“先查询、再写入”假装保证并发安全。
- 不用进程内锁承担多 worker 或多实例一致性。

数据库提交后的尽力而为外部操作，不得反向伪装成数据库回滚；明确重试、补偿和可观测性策略。

### 6. 保护安全边界

- 所有权、租户和软删除条件进入数据库查询。
- 不记录或返回密码、Token、连接串、完整凭据 URL、SQL 或第三方原始敏感响应。
- 对必须按产品契约返回的敏感字段，执行项目规定的鉴权、响应头、缓存和日志保护。
- API Response 使用显式 Schema，不依赖隐式 ORM 序列化。
- 错误响应不包含堆栈或基础设施细节。
- 项目自身的数据分类和披露规则优先于通用默认值。

### 7. 编写分层测试

按本次行为选择：

- Service 单元测试：规则、权限、状态转换、提交和回滚。
- Repository 集成测试：真实数据库语义、约束、事务和并发。
- API 契约测试：校验、状态码、错误码、响应字段和依赖覆盖。
- Adapter 测试：超时、无效响应、降级和敏感信息过滤。
- 迁移测试：空库升级、已有版本升级、回填和约束。

使用实现稳定接口的轻量 Fake；不要用 SQLite 推断 PostgreSQL 专有行为，也不要用无规格 Mock 隐藏接口漂移。

### 8. 验证与交付

运行仓库实际支持的格式化、静态检查、目标测试和相关回归测试；不要虚构命令。至少再执行：

```bash
git diff --check
git status --short
```

若环境、依赖或数据库不可用，明确区分已通过、失败和未执行项。

最终说明：

- 实现结果与主要设计。
- 修改文件及职责。
- API、事务、并发和迁移影响。
- 调用方或配置变化。
- 已执行的检查及未验证风险。
- 敏感信息边界是否得到保护。
