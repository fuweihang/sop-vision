整理用户指定范围内的项目文档，使当前事实、待执行工作和历史影响各有明确位置。本任务只修改
文档及引用文档的入口，不修改业务代码。

## 确定事实和范围

1. 阅读适用的仓库说明、`docs/README.md`、`docs/plans/README.md` 和目标模块下的 `AGENTS.md`，
   再检查 `git status`，保留用户已有修改。
2. 以用户指定的目录或文件为修改范围。用户只说“整理文档”时，检查仓库 README、`docs/` 及其
   引用的相关代码、配置和测试；只在修复文档入口或链接时修改范围外的 README 等文档。
3. 当前运行行为以代码、迁移、生成契约、测试和配置为事实来源，优先级遵循 `docs/README.md`。
   产品目标、历史决定、合规要求和未实施计划不能只从代码推断。
4. 遇到冲突时说明差异；能够确认时修正文档，不能确认时保留并标记待核实。修改或删除前检查
   站内链接和明显的外部引用。

## 按目录放置信息

- `docs/modules/<module>/`：已经实现的能力、模块边界、接口、配置、故障行为、当前限制、排障和
  验证入口。不得放待办步骤或完成进度。
- `docs/plans/<work-item>/`：尚未完成且可直接执行的目标、步骤、依赖和验收。计划引用模块文档中的
  当前事实，不复制长期规则。
- `docs/changes/`：已经交付的用户可见行为、API、配置、数据、兼容性和安全影响。遵循该目录的
  `README.md`；它是整理后的交付历史，不是逐文件 diff。
- `docs/decisions/`：跨模块、长期有效且修改成本较高的技术取舍及原因。模块内部规则继续由模块
  文档负责。
- 产品、总体架构、Design System、原型和其他文档按照 `docs/README.md` 的职责维护，不为目录整齐
  做无实际价值的迁移。

同一事实只保留一个所有者，其他文档使用链接。当前存在的限制写入模块文档；需要后续实施的解决
工作写入计划，不能把待办重新混入长期能力说明。

## 清理内容

优先移除或重写：

- 阶段进度、完成记录和时间线式流水账；
- 已解决问题的排查过程；
- 临时调试、失败尝试和中间状态；
- Git diff 式“新增/修改了什么”的流水账；不得因此删除 `docs/changes/` 中符合目录规则的交付记录；
- 可直接从代码明显看出的单点实现细节；
- 重复、失效或已被实现淘汰的描述。

不要简单摘要旧文档。将仍有价值的信息重写为：

- 当前系统状态和已实现能力；
- 架构、模块职责和关键数据流；
- 重要设计决策及其原因；
- 跨模块约束、系统不变量和非显而易见规则；
- 当前仍存在的风险、技术债和限制，以及对应的未完成计划链接。

判断是否保留一段信息的标准：

> 删除它是否可能导致未来 AI 对系统产生错误理解或做出错误修改？
> 如果不会，优先删除。

## 删除限制

- ADR、`docs/changes/`、发布记录、合规或审计记录、许可证、贡献指南、运维手册和用户明确要求
  保留的文件，不得仅因内容较旧而删除。
- 不为减少文件数量而合并职责不同的文档。删除文件前确认精确目标，不使用宽泛路径或未解析的
  通配符。发现代码问题时只记录为待处理事项。

## 完成计划的处理

只有计划对应的代码和必要验证已经完成，才按以下顺序处理：

1. 把当前能力、接口、配置、故障、排障和验证入口写入对应 `docs/modules/` 文档。
2. 按 `docs/changes/README.md` 新增交付记录；不能用原计划或提交列表代替。
3. 只有形成跨模块长期取舍时，才新增或更新 `docs/decisions/`。
4. 更新 README、架构、产品和其他文档中的入口及引用。
5. 确认没有未完成事项和引用依赖后，从 `docs/plans/` 删除已完成计划。

完成的计划不在仓库中归档，也不改名为“已完成”；Git 历史保存执行过程。部分完成的计划只移出
已完成部分，剩余目录继续只描述未完成工作。

## 完成标准

整理后的文档应让第一次进入项目的 AI 快速知道：

- 项目目标和当前阶段；
- 当前架构及模块关系；
- 已实现能力及当前限制；
- 必须遵守的关键决策和约束；
- 未完成事项对应的执行计划；
- 下一阶段应从哪里继续。

完成前检查：

- `docs/modules/` 中没有实施步骤或完成进度，当前事实也没有只留在 `docs/plans/`；
- `docs/plans/` 中没有已完成计划，仓库中没有旧的 `docs/plan/` 路径；
- `docs/changes/` 与 `docs/decisions/` 没有被误当作过程文档清理；
- 本地链接、相对路径和 Markdown 格式正常，并执行与文档变化相称的项目检查。

完成后简要说明：

- 合并、删除和保留了哪些类型的内容；
- 关键知识被放到哪里；
- 发现了哪些无法确认的文档与代码差异；
- 实际执行了哪些链接或项目检查。

如果删除了受 Git 跟踪的文件，说明可以从版本历史恢复。不要输出逐文件修改流水账。
