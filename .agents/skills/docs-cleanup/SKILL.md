整理项目文档，使其从“开发过程记录”转变为“后续 AI 可直接依赖的项目知识”。

## 执行要求

1. 检查 `docs/`、README、相关代码、配置和测试，以**当前代码为最终事实来源**；修正文档与代码不一致之处。
2. 清理以下低价值内容：

   * 阶段进度、完成记录和时间线式流水账；
   * 已解决问题的排查过程；
   * 临时调试、失败尝试和中间状态；
   * Git diff 式“新增/修改了什么”的记录；
   * 可直接从代码明显看出的单点实现细节；
   * 重复、失效或已被实现淘汰的描述。

3. 不要简单摘要旧文档。将仍有价值的信息重写为：

   * 当前系统状态和已实现能力；
   * 架构、模块职责和关键数据流；
   * 重要设计决策及其原因；
   * 跨模块约束、系统不变量和非显而易见规则；
   * 当前仍存在的风险、技术债和待办。

4. 判断是否保留一段信息的标准：

   > 删除它是否可能导致未来 AI 对系统产生错误理解或做出错误修改？
   > 如果不会，优先删除。

5. 已完成的阶段性计划，在有效知识迁移到长期文档后可以删除或合并。不要为了保存历史而保留；Git 负责历史追踪。
6. 减少重复和文档数量。重要事实应尽量只有一个权威来源，不要为了分类而创建大量新文件。
7. 本任务只整理文档，不修改业务代码。发现代码问题时仅记录为待处理事项。

## 完成标准

整理后的文档应让第一次进入项目的 AI 快速知道：

* 项目目标和当前阶段；
* 当前架构及模块关系；
* 已实现能力；
* 必须遵守的关键决策和约束；
* 当前未完成事项、风险和技术债；
* 下一阶段应从哪里继续。

完成后仅简要说明文档的合并、删除、关键知识提炼以及发现的文档/代码不一致，不输出逐文件修改流水账。
