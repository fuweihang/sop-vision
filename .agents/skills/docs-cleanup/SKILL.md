整理用户指定范围内的项目文档，使其从开发过程记录转变为后续开发可以直接依赖的当前信息。本任务只修改文档，不修改业务代码。

## 确定事实和范围

1. 阅读适用的仓库说明，检查 `git status`，保留用户已有修改。
2. 以用户指定的目录或文件为修改范围；用户只说“整理文档”时，检查 README、`docs/` 及其引用的相关代码、配置和测试，不自动扩展到其他类型文件。
3. 当前运行行为以代码、测试和配置为事实来源；产品目标、历史决策、合规要求和未实施计划不能只从代码推断。遇到冲突时说明差异，能够确认时修正文档，不能确认时保留并标记待核实。
4. 修改或删除前检查站内链接和明显的外部引用，避免留下失效入口。

## 清理内容

优先移除或重写：

- 阶段进度、完成记录和时间线式流水账；
- 已解决问题的排查过程；
- 临时调试、失败尝试和中间状态；
- Git diff 式“新增/修改了什么”的记录；
- 可直接从代码明显看出的单点实现细节；
- 重复、失效或已被实现淘汰的描述。

不要简单摘要旧文档。将仍有价值的信息重写为：

- 当前系统状态和已实现能力；
- 架构、模块职责和关键数据流；
- 重要设计决策及其原因；
- 跨模块约束、系统不变量和非显而易见规则；
- 当前仍存在的风险、技术债和待办。

判断是否保留一段信息的标准：

> 删除它是否可能导致未来 AI 对系统产生错误理解或做出错误修改？
> 如果不会，优先删除。

## 删除限制

- ADR、变更日志、发布记录、合规或审计记录、许可证、贡献指南、运维手册和用户明确要求保留的文件，不得仅因内容较旧而删除。
- 阶段性计划只有在已完成、仍有效的信息已迁移到长期文档、没有未完成事项且没有引用依赖时，才可以删除或合并。
- 不为减少文件数量而合并职责不同的文档。重要事实尽量只有一个明确来源，其他位置使用链接而不是复制。
- 删除文件前确认精确目标，不使用宽泛路径或未解析的通配符。发现代码问题时只记录为待处理事项。

## 完成标准

整理后的文档应让第一次进入项目的 AI 快速知道：

* 项目目标和当前阶段；
* 当前架构及模块关系；
* 已实现能力；
* 必须遵守的关键决策和约束；
* 当前未完成事项、风险和技术债；
* 下一阶段应从哪里继续。

完成后简要说明：

- 合并、删除和保留了哪些类型的内容；
- 关键知识被放到哪里；
- 发现了哪些无法确认的文档与代码差异；
- 实际执行了哪些链接或项目检查。

如果删除了受 Git 跟踪的文件，说明可以从版本历史恢复。不要输出逐文件修改流水账。
