# Code Explain

只读分析当前实现，向用户解释代码如何工作。不要修改任何文件。

## 目标

不要逐文件、逐函数复述代码。

重点回答：

1. 核心 runtime 代码之间如何协作完成该功能？
2. 每个核心模块内部如何运作？
3. tests 如何验证这些行为？
4. types / schemas / models 如何约束模块之间的数据关系？

## 分析范围

优先查看：

- 用户指定的方案或任务
- 相关设计/计划文档
- git diff / git log
- runtime 实现代码
- tests
- types / schemas / models
- 配置和外部接口

优先理解 runtime 主流程。

tests 和 types 只做辅助解释，不要逐个测试、逐个类型罗列。

忽略：

- 样板代码
- 简单 getter/setter
- 普通 UI 微调
- 无关历史代码
- 对理解主流程没有帮助的类型声明
- 重复性测试

## 分析方式

从“运行流程”而不是“目录结构”理解代码。

沿真实调用链追踪：

入口
→ 调度/协调
→ 核心业务逻辑
→ 状态/数据处理
→ 外部依赖
→ 最终结果

同时识别：

- 哪些 types 定义模块间的数据契约
- 哪些 tests 覆盖主流程、边界条件和关键异常

## 输出要求

使用简洁中文，尽量少用黑话。

### 1. 整体作用

用 3～6 句话说明：

- 这次实现解决什么问题
- 核心设计是什么
- 主要由哪些部分协作完成

### 2. 核心代码关系

只列真正重要的 runtime 模块。

例如：

`API → Service → Repository → Database`

解释：

- 谁调用谁
- 数据如何传递
- 每个模块的职责

必要时使用 Mermaid。

### 3. 一次完整执行流程

从真实入口开始，按实际运行顺序解释。

每一步指出：

- 进入哪个文件 / 类 / 函数
- 做了什么
- 数据发生什么变化
- 为什么进入下一模块

重点讲调用链和因果关系。

### 4. 核心模块内部原理

对每个核心 runtime 模块说明：

**`文件路径 / 核心符号`**

- 职责
- 输入
- 内部关键流程
- 依赖
- 输出
- 必要时说明异步、缓存、并发、生命周期、错误处理等机制

不要解释显而易见的代码。

### 5. 数据与 Types

简要说明真正重要的：

- request / response schema
- domain model
- DTO
- enum / union
- 状态类型
- 模块间共享的数据结构

重点回答：

- 数据从哪里产生
- 经过哪些类型转换
- 哪个类型是模块之间的契约
- 哪些字段决定核心行为

例如：

`CameraCreateRequest`
→ `CameraConfig`
→ `Camera`
→ `CameraResponse`

不要逐字段解释，除非字段直接影响核心逻辑。

### 6. Tests 如何验证实现

简要说明测试体系，不要逐个 test case 复述。

重点指出：

- 哪些测试覆盖 runtime 主流程
- 哪些测试覆盖关键边界情况
- 哪些测试验证错误处理
- mock / fixture / fake 分别替代了什么真实依赖
- 哪些核心行为目前缺少测试（如果明显存在）

优先按“行为”归类，例如：

- 正常创建流程
- 重复资源处理
- 外部服务失败
- 状态同步
- 数据转换

而不是按测试文件机械罗列。

### 7. 数据和状态如何流动

如果涉及数据、状态或消息流，说明：

`来源 → 类型转换 → 核心处理 → 状态/存储 → 输出`

重点指出数据在哪些位置发生关键变化。

### 8. 最值得理解的设计点

只挑几个真正影响理解的点：

- 为什么需要这一层抽象
- 哪个模块是核心协调者
- 为什么需要某个重要 type
- tests 暗示了哪些业务约束
- 哪些代码看似独立但存在重要依赖

不要做泛泛的架构评价。

### 9. 推荐阅读顺序

如果用户之后只准备亲自看少量代码，推荐 3～6 个最值得看的文件/符号。

顺序优先：

1. runtime 主入口
2. 核心协调模块
3. 核心业务模块
4. 关键 type/schema
5. 最能体现行为的测试

每项只说明一句“为什么值得看”。

## 表达原则

- 面向“想理解实现，但不想逐行看代码”的开发者。
- runtime 是主角，tests 和 types 是辅助。
- 优先解释因果关系和调用关系。
- 不要机械复述函数名、类型名、测试名。
- 不要输出大段源码。
- 不要把所有文件称为核心代码。
- 胶水代码直接略过。
- tests 重点解释“验证了什么”，而不是“怎么写的”。
- types 重点解释“约束了什么”，而不是逐字段介绍。
- 无法从代码确认的行为明确说明，不要猜测。
