# 代码讲解

只读分析用户指定的实现范围，帮助开发者理解代码如何协作完成实际行为。不要修改文件，也不要把讲解变成代码评审。

## 确定范围

- 用户指定功能、提交、方案、文件或符号时，以该目标为起点；仅在理解调用链所需时扩展到相邻代码。
- 用户没有给出明确目标时，先从当前变更、最近相关提交或用户描述中寻找范围。仍无法确定时，说明缺少的目标，不要讲解整个仓库。
- 优先读取 runtime 入口、核心调用方与被调用方、关键类型、配置和测试。忽略样板代码、简单访问器、重复测试及与主流程无关的声明。
- 以当前代码、测试和配置能够确认的行为为事实。设计文档与实现冲突时，指出差异，不自行猜测哪一方代表未来需求。

## 追踪实现

从真实入口沿可达调用链分析：

```text
入口 → 调度或协调 → 核心业务处理 → 数据或状态变化 → 外部依赖 → 结果
```

重点确认：

- 每一步由哪个文件、类或函数负责，为什么会进入下一步。
- 数据在哪里产生、转换、校验、持久化或返回。
- 哪些 schema、model、DTO、enum 或状态类型会直接改变核心行为。
- 异步、缓存、并发、事务、生命周期和错误处理是否影响实际执行顺序。
- 测试验证了哪些主流程、边界条件和失败路径，哪些关键行为明显缺少测试。

无法从代码确认的内容应标记为推断或未知。不要用函数名、注释或测试名称替代对实现的检查。

## 输出

根据问题复杂度选择必要内容，不要求固定输出所有章节。

普通功能通常包括：

1. **整体作用**：用几句话说明解决的问题、真实入口和主要协作模块。
2. **核心调用链**：使用一行调用关系或必要的 Mermaid 图，解释谁调用谁以及数据如何传递。
3. **一次完整执行流程**：按运行顺序说明关键步骤、状态变化和输出。
4. **关键实现依据**：给出相关文件与核心符号；环境支持时附具体行号，方便用户直接核对。

仅在确实影响理解时补充：

- 数据类型与状态流转。
- 异步、缓存、事务、并发、资源生命周期或错误传播。
- 测试覆盖与明显遗漏。
- 重要设计取舍。
- 3～6 个文件或符号的推荐阅读顺序。

用户只问一个函数或局部分支时，直接回答该问题，不扩展成完整系统报告。用户要求深入分析时，再增加模块内部流程和更多证据。

## 表达要求

- 解释因果关系和运行行为，不逐文件、逐函数复述。
- runtime 是主角，tests 和 types 只用于说明约束与证据。
- 不输出大段源码，不解释显而易见的胶水代码。
- 不把潜在缺陷作为评审 finding 展开；若发现明显问题，只简短指出并建议另行执行代码评审。
