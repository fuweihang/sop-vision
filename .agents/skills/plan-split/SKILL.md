# 方案拆分检查

在开始编写代码前，先审核当前已经生成的实施方案。

如果该方案规模过大，不适合在单个 Codex 会话中高质量完成，则将其拆分为多个**按顺序执行、可独立交付**的任务。

出现以下情况时应优先拆分：

* 涉及多个相对独立的模块、架构层或功能；
* 修改范围较大，跨越较多文件或系统边界；
* 包含多个可以独立验证的阶段；
* 单次执行可能导致上下文过长、遗漏约束或降低代码质量；
* 后续阶段需要依赖前一阶段的实际实现结果才能可靠继续。

拆分要求：

1. 每个任务对应一个明确、可验证的阶段性交付物。
2. 每个任务生成独立 Markdown 文件并放入 `docs/`。
3. 每个任务文档应包含：

   * 任务目标
   * 当前上下文 / 前置条件
   * 实施范围
   * 明确不做的事项
   * 实施步骤
   * 验证方式
   * 完成标准
   * 与下一任务的衔接信息

4. 每个任务必须包含新 Codex 会话执行时所需的必要上下文，不得依赖当前会话中的隐式信息。
5. 不要按文件机械拆分，应按可独立验证的功能、架构阶段或交付物拆分。
6. 任务之间允许存在顺序依赖，但每个任务都必须适合：

   * 新建独立 Codex 会话执行；
   * 独立审核；
   * 独立实现；
   * 独立验证。

完成拆分后，**不要执行代码修改**。

仅输出：

* 是否需要拆分；
* 拆分原因；
* 任务执行顺序；
* 生成的 Markdown 文件列表；
* 推荐首先执行的任务。

如果方案规模较小、职责单一，并且可以在一次会话中可靠实现和验证，则明确说明无需拆分。
