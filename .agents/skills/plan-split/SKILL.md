# 方案拆分检查

在开始编写代码前，检查用户指定的已有实施方案。读取相关项目计划和当前代码，只获取判断任务规模、依赖关系及验证方式所需的上下文。

如果该方案规模过大，不适合在单个 Codex 会话中高质量完成，则将其拆分为多个**按顺序执行、可独立交付**的任务。

出现以下情况时应优先拆分：

* 涉及多个相对独立的模块、架构层或功能；
* 修改范围较大，跨越较多文件或系统边界；
* 包含多个可以独立验证的阶段；
* 单次执行可能导致上下文过长、遗漏约束或降低代码质量；
* 后续阶段需要依赖前一阶段的实际实现结果才能可靠继续。

拆分要求：

1. 每个任务对应一个明确、可验证的阶段性交付物。
2. 每个任务的内容应包含：

   * 任务目标
   * 当前上下文 / 前置条件
   * 实施范围
   * 明确不做的事项
   * 实施步骤
   * 验证方式
   * 完成标准
   * 与下一任务的衔接信息

3. 每个任务必须包含新 Codex 会话执行时所需的必要上下文，不得依赖当前会话中的隐式信息。
4. 不要按文件机械拆分，应按可独立验证的功能、架构阶段或交付物拆分。
5. 任务之间允许存在顺序依赖，但每个任务都必须适合：

   * 新建独立 Codex 会话执行；
   * 独立审核；
   * 独立实现；
   * 独立验证。

完成拆分后不要实施业务代码，也不要审核每个子任务的方案质量。

默认在回复中给出拆分结果，不创建文件。只有用户明确要求落盘时才生成 Markdown：优先使用用户指定目录；未指定时使用 `docs/plans/`，并避免覆盖已有文件。

最终回复仅说明：

* 是否需要拆分；
* 拆分原因；
* 任务执行顺序；
* 已生成的 Markdown 文件列表（仅在实际落盘时）；
* 推荐首先执行的任务。

如果方案规模较小、职责单一，并且可以在一次会话中可靠实现和验证，则明确说明无需拆分。
