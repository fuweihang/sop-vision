# 代码评审

对用户指定范围进行只读审查，优先找出会造成错误结果、安全风险、数据问题或线上故障的缺陷。默认不修改代码；只有用户明确要求修复时，才能进入修改流程。

## 评审边界

- 用户已指定 diff、提交、PR、文件或目录时，只审查该范围。用户仅要求审查“当前变更”时，以工作区和暂存区的 diff 为范围。
- 读取变更文件的完整上下文，并按需检查调用方、被调用方、测试、配置、迁移和文档。不要只根据孤立的 diff 片段下结论。
- 主要报告本次变更新增、恶化或直接暴露的问题。不要把无关的历史问题算到当前变更；若历史行为使新增代码必然出错，指出相关证据并把位置落在变更行上。
- 如果找不到可评审的变更或目标，不要猜测范围。说明缺少什么，并请用户提供目标。
- 评审授权不包含修改文件、提交代码、发送评论或操作远程系统。

## 评审流程

### 1. 确定意图和范围

1. 读取适用的仓库说明和用户需求。
2. 查看状态、diff 和变更文件全文，确认变更想解决什么问题。
3. 找到受影响的入口、调用链、数据流、外部接口和已有测试。
4. 需求不完整时采用保守解释，并在最终结果中单独列出关键假设。

### 2. 用证据检查风险

沿实际可达路径检查正常流程、边界条件和失败路径。一个 finding 至少应具备：

- 可触发的输入、状态、并发顺序或部署条件；
- 能从代码、测试、类型、配置、接口说明或可靠文档中确认的证据；
- 具体且有实际影响的结果；
- 与现有设计相符的最小修改方案。

证据不足时继续检查相关上下文。仍无法确认的内容放入“问题与假设”，不要伪装成确定缺陷。

根据变更内容选读 [专项风险检查](references/review-checklist.md) 中相关章节：

- 数据库写入、缓存、队列或共享状态：读取“数据、事务与并发”。
- 用户输入、鉴权、文件、命令或外部 URL：读取“安全边界”。
- 重试、异步任务、资源生命周期或外部服务：读取“可靠性与恢复”。
- 公共 API、Schema、配置、迁移或序列化：读取“兼容性与发布”。
- 热路径、批处理或大数据量：读取“性能与容量”。
- 模块职责、重复规则、隐式依赖或测试隔离：读取“可维护性与可测试性”。
- 普通业务逻辑：读取“正确性与错误处理”；没有对应风险时不必加载其他章节。

### 3. 验证结论

- 在安全且与范围相符时，运行最小必要的测试、类型检查或静态检查。不要因为测试通过就断言没有问题。
- 无法运行验证时，明确说明未验证的部分及原因，不要声称已经验证。
- 检查每个 finding 是否能在具体位置修复。只能给出宽泛改进方向的内容通常不应报告。

## 严重程度

- **P0 — Critical**：可造成严重权限绕过、敏感数据泄露、不可恢复的数据损坏或大范围服务故障，必须阻止合并。
- **P1 — High**：存在可触发的明确 Bug、数据不一致、重要功能失败、并发错误或显著可靠性问题，原则上应在合并前修复。
- **P2 — Medium**：存在有证据支持的健壮性、可测试性或维护性问题，会增加实际故障概率或后续修改风险，但通常不阻止当前合并。
- **P3 — Low**：影响范围较小但仍有具体后果的缺陷或改进。

严重程度按实际影响和触发概率判断，不按修改工作量判断。

## 输出格式

先列 findings，并按 P0 到 P3 排序。每个 finding 包含：

```text
[P1] 简短、具体的问题标题

位置：path/to/file:line
证据：什么条件会触发，代码如何到达该结果
影响：会造成什么实际后果
建议：最小且可执行的修改方式
```

位置应尽量落在本次变更行，并缩小到足以理解问题的范围。相同根因只报告一次；必要时补充其他受影响位置。

Findings 后按需输出：

1. **问题与假设**：只放影响结论的未确认信息。
2. **验证**：列出实际运行的检查和未能验证的关键部分。
3. **结论**：只选择一个结果。

结论规则：

- `REQUEST_CHANGES`：存在 P0/P1，或缺少的信息使变更无法被安全接受。
- `APPROVE_WITH_SUGGESTIONS`：只有非阻断的 P2/P3。
- `APPROVE`：没有达到报告门槛的问题。

没有 finding 时明确写“未发现需要处理的问题”，同时说明仍存在的验证限制。不要为了填充结果而虚构优点或风险。
