# 专项风险检查

只读取与当前变更直接相关的章节。清单用于提醒容易遗漏的工程风险，不要求逐项输出，也不能替代代码证据。

## 正确性与错误处理

- 条件、范围、单位、时区、精度、默认值和类型转换是否符合需求。
- 空值、空集合、重复输入、极端值、非法状态和部分缺失数据是否会走到错误分支。
- 状态变化是否完整，失败后是否留下调用方无法识别的半完成状态。
- 错误是否被吞掉、错误类型是否被错误转换、原始上下文是否丢失。
- 新增默认行为或副作用是否与函数、接口和调用方预期一致。
- 测试是否覆盖最容易出错的分支，而不是只验证正常路径。

## 数据、事务与并发

- 多次写入是否需要同一事务；中途失败是否产生部分成功或数据不一致。
- 读取后写入、检查后创建、计数后更新等流程是否存在竞态条件。
- 重复请求、消息重投或任务重启是否造成重复写入；幂等键是否稳定并覆盖完整操作。
- 锁、事务隔离级别、唯一约束和原子更新是否与真实并发模型匹配。
- 缓存更新和失效顺序是否可能返回长期脏数据，或在失败时丢失权威数据。
- Schema 和迁移是否允许新旧版本服务同时运行；回滚是否仍能读取已经写入的数据。

## 安全边界

- 外部输入是否在进入 SQL、命令、模板、文件路径、URL 或反序列化流程前受到正确约束。
- 鉴权是否只验证“已登录”却遗漏资源归属、租户、角色或具体操作权限。
- 服务端请求是否允许访问内网、元数据地址、任意协议或重定向后的未校验地址。
- 文件路径是否可越过允许目录；上传内容是否只信任扩展名或客户端 MIME 类型。
- Token、密码、密钥、个人信息和业务敏感字段是否进入日志、错误响应或监控标签。
- 加密、签名、随机数和比较操作是否使用适合安全用途的标准实现。
- 安全问题必须给出可到达路径；仅看到“用户输入”不能直接判定存在漏洞。

## 可靠性与恢复

- 超时、取消和依赖失败是否能传递到正确边界，资源是否在所有退出路径释放。
- 重试是否有上限、退避和明确的可重试条件；重试写操作是否保持幂等。
- 第三方调用响应超时时，系统能否区分“操作失败”和“操作成功但响应丢失”。
- 队列消费、定时任务和后台工作在进程退出或重启后是否会丢失、重复或永久卡住。
- 连接、文件、锁、线程、goroutine、订阅和临时资源是否存在泄漏路径。
- 降级、熔断和兜底是否会隐藏数据错误，或把临时失败永久保存为成功结果。
- 日志和错误信息是否包含定位所需的请求、实体和依赖信息，同时避免敏感信息泄漏。

## 兼容性与发布

- 公共 API 的字段、状态码、错误格式、排序、分页和默认值是否保持兼容。
- 序列化格式、事件消息、数据库字段和配置是否能被仍在线的旧版本读取。
- 新增必填字段是否有安全默认值；删除或重命名是否经过分阶段发布。
- 启动顺序、健康检查和 graceful shutdown 是否与部署方式匹配。
- 配置错误是否在启动阶段明确失败，而不是运行到关键路径才暴露。
- 迁移是否可能长时间锁表、全表重写或依赖尚未部署的代码。

## 性能与容量

只有当仓库上下文能说明数据规模、调用频率或资源限制时，才报告性能 finding。

- 热路径是否新增无界循环、重复计算、N+1 查询或逐项网络请求。
- 集合、队列、缓存、批次和响应体是否有明确上限或分页。
- 大对象是否被不必要地整体加载、复制、序列化或保留。
- 锁和阻塞调用是否出现在高并发关键路径，并有实际争用条件。
- 优化建议应说明触发规模和复杂度变化。

## 可维护性与可测试性

- 同一业务规则是否被复制到多个会独立变化的位置，并已存在不一致风险。
- 模块是否直接依赖其他模块的内部数据或隐式全局状态，使局部修改影响不可预测。
- 时间、随机数、网络、数据库等副作用是否与核心判断混合到无法稳定验证关键分支。
- 公共接口是否名称与副作用明显不符，容易让调用方错误使用。
- 为测试增加抽象时，应能隔离真实外部依赖；不要为了 mock 简单纯函数而制造接口层。
