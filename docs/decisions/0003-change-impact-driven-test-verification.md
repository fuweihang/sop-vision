# 0003｜使用变更影响表驱动日常测试验证

## 背景

Backend 与 Frontend 曾按源码位置分散测试，公共 Fixture、跨端契约和外部依赖检查缺少统一归属。
开发者需要手工选择 Pytest、Vitest 和专项脚本，容易漏掉跨模块影响；每次都运行全部检查又会增加
等待时间和输出噪声。

## 决定

- 业务测试从源码目录分离，统一使用“平台 / 测试层级 / 主模块”目录；公共测试辅助代码放在各测试
  根的 `support/` 中。
- `test-impact.json` 是生产路径、测试路径、模块传播、验证强度和实际命令的唯一登记表。
- 日常交付只调用 `./scripts/verify-changed.sh`。入口先检查全仓测试目录，再根据 Git 变更、模块影响和
  变更规模选择 `unit`、`module` 或 `integration` 强度。
- 未登记的生产路径和归属不唯一的测试都阻止交付，不通过默认运行全量测试来掩盖登记遗漏。
- CI 和发布验收继续运行完整测试、静态检查、构建及真实环境门禁；按变更验证不替代这些独立目的。

当前目录、选择和排障规则见[测试基础设施](../modules/test-infrastructure/README.md)。

## 影响

- 新增模块、测试层级、Support 或质量命令时，必须同时更新影响表和测试工具回归测试。
- 业务模块只维护自身测试内容，不在 README、Skill 或脚本中复制另一份命令映射。
- 变更选择依赖正确的 Git 基准和路径登记；基准不可用或环境依赖缺失时必须失败并说明原因。
- E2E 与视觉测试在具备独立环境和产物管理前，不加入日常验证升级链。

## 调整条件

当仓库规模或 CI 数据证明当前路径规则和规模阈值无法稳定控制反馈时间，或引入需要独立调度的 E2E、
视觉、硬件测试时，重新评估影响表结构和执行器。调整时仍需保持测试唯一归属、未登记路径失败以及
本地日常验证与完整发布验收分离。
